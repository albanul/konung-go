# LAN version (network play)

The single-player `konung.exe` has no network code (imports only GDI32, KERNEL32, USER32, WINMM, DSOUND, DDRAW; dynamic loads only `MP.DLL` and `VORBISFILE.DLL`). Network play is a separate program, `LAN_KONG.EXE` (PE timestamp 23.03.2003, `BEGTEXT` 0x54200 bytes against 0x37E00 in `konung.exe`). Fan accounts call the online variant "сетевой Князь": up to 16 players, 3 nations, 180-minute sessions, amulet carrying and PvP ([fan page](https://gospitaliers.narod.ru/knyaz_server.htm), unverified).

**Port decision:** our own network layer (not wire-compatible with `LAN_KONG.EXE`). The game rules come from the LAN exe; the transport is ours.

## Layout

The LAN files live in the game folder (`assets/Konung`) next to the single-player files, as in the original install: the GOG folder already held the LAN version's `GAME.RES`, `HISCORES.DAT`, `SERVER.LOG` and `Servers.cfg`, which `konung.exe` never opens. Names do not clash; `GAME.RES`, `LIGHTS.RES` and `SERVER.LOG` were byte-identical, and `HISCORES.DAT` is the LAN one (the GOG one was all zeros). The game only joins: sessions run on the dedicated server, a separate binary (`cmd/konung-server`, below); the game has no command-line modes and does not host.

## Port status

* Main menu «Сетевая игра» (port addition, `internal/game/lan.go`): opens the LAN menu (below). Shown only without a running game and only when `LAN_KONG.EXE`, `ME800R.RES` and `PLAY800R.RES` are in the game folder. The label is the large exe font (`FontLargeVA`) scaled 2×, tinted like the painted buttons (normal ≈ `MENU800R.RES` frame 9 lettering, selected ≈ frame 10), at (262, 196), where «Сохранить игру» is drawn in a game.
* Images: `go run ./cmd/res-gallery` → `output/site/lan`. Maps: `go run ./cmd/map-render -mapsres assets/Konung/MAPS.RES -all output/site/lanmaps`.
* LAN screens (`internal/game/lanui.go`, data from the exe via `gamestate.ParseLANExe`): the LAN menu, the rating screen (frame only), the login screen with typing, Tab, «Сохранить пароль», the portraits, the server list (LAN search on entering; Enter in the address field searches that address too), joining, the message box, «Ok» → wait, and `LAN.CFG` read and written in the original layout (`gamestate.LANConfig`). Verified under Xvfb (then still with in-game hosting): discovery, join, the duplicate-name refusal, wait and cancel.
* Network layer `internal/netplay` (adapted from the author's go-tetris `pkg/network`, MIT): newline-delimited JSON messages over TCP (`Conn`: ordered, keep-alive pings, a stalled peer is disconnected instead of messages being dropped, graceful close with a TCP half-close), a session server (`Listen`: join handshake with protocol version, name, password, clan and hero model; up to 16 players; chat; `MsgGame` handed to `OnGame`; membership messages in one order for everyone), a client (`Dial`) and LAN discovery (`ServeDiscovery`/`Discover`: UDP broadcast on the game port, replacing DirectPlay's session list). Port 7777 for both, as the original's TCP/IP port.
* Server settings (`cmd/konung-server/config.go`): name, port, max players, session minutes, world speed and team damage in one file, `DIR/server.conf` or `-config FILE` (`key = value`, `#` comments; [`konung-server.conf.example`](../konung-server.conf.example) shows every key; an unknown key or bad value stops the server). Order: defaults, the `SERVER` file (name, minutes), the config, then the flags given. `scripts/konung-server.sh` copies `konung-server.conf` from the repo root into the server at every start and takes the host port from its `port`.
* Dedicated server `cmd/konung-server` (`-data DIR`, `-config`, `-port`, `-max`, `-name`, `-minutes`, `-speed`, `-team-damage`; `Containerfile` for a container, `scripts/konung-server.sh` to run it: `KONUNG_NAME="…" scripts/konung-server.sh restart` names the server, and the container is re-created at each start so settings apply): accounts and progress in SQLite (`DIR/konung.db`, `internal/lanstore`), session name and length from `DIR/SERVER` if present, LAN discovery on the game port, the session clock with the rating update at each end. First login creates the account (the server logs «Новый игрок <name> клан <clan>»); a wrong password shows «Неправильный пароль»; after joining, the login screen shows the account's hero in the «Параметры»/«Навыки» boxes (at the anchor points).  Verified end to end under Xvfb with the real server: account created, wrong password refused, rejoin with the stored hero, leave, session ends.
* Entering the world: «Ok» sends `MsgEnter` with the hero type; the server puts the hero into its world in the first free slot (0–15) on the type's start ([game start](#game-start)) and answers `MsgEntered` with the map, cell, facing and slot; the client builds the viewer ([server world](#server-world)). A server without the world files refuses entering («this server has no world»). Saving is hidden in a LAN world; starting or loading a single-player game drops the connection.
* Other players, villagers and creatures: what the server reports of the own hero's map ([server world](#server-world)); a player's hero is named by its account (`Game.Names`), the cursor over it shows «<name>, клан <clan>».
* Port choices: no hosting from the game — the list leaves out the original's row 0 «Новый сервер» and shows only the sessions found; one connection type (the port's TCP/IP), so the list skips the original's DirectPlay connection stage; the list shows session names (with the host's address only when names repeat); the scroll arrows are clickable (the original's 800×600 rectangles were copied from the NEW screen); a name already in the session is refused with a port message («Ошибка: Игрок с таким именем уже в игре»; the original's reconnect path `0x00447CF8` is not ported); Escape in the LAN menu returns to the port's main menu; text uses the single-player fonts (`FontSlotVA`, focused `FontLargeVA`) — the LAN exe's fonts `0x7A5142`/`0x7AB36F` are not mapped.
* Server differences, on purpose: passwords are stored as salted PBKDF2-SHA256 hashes (the original kept them in plain text); accounts and items are SQLite rows, not fixed `0x80` / `0x200`-byte records; there is no 7-character password limit on the server (the client field still allows 7); a participant is marked at join, not at «Ok» (`0x4C` has no port counterpart yet).
* «Новый герой» (`gamestate/lanhero.go`, `game/lannewhero.go`; [new hero](#new-hero)): the NEW800R screen with the class, combat and peaceful skill, the stat trade on the LAN tables, «Макс. груз» / «Макс. отряд», the clan field and list (`CLANS.CFG`, typed clans and the server's list from the welcome), the hero preview and its look; «Ok» keeps the build, and the next join warns «Старый персонаж будет удален!» (message 1, Ok/Отмена) and sends it (`JoinInfo.NewHero`). The server checks the choices with the screen's own rules (`LANHeroChoice.Build`) and rebuilds the account's hero. Verified under Xvfb with the dedicated server: the screen, the warning, the rebuilt hero on the login screen.
* LAN mode (`game/menu.go`, `lanui.go`): «Сетевая игра» opens the LAN menu, which stays until «Выход»; Escape in a LAN world opens it with «Вернуться в игру» and «Закончить игру» (ME800R frames 3 and 15, as the original in a game), the hero staying online meanwhile; «Закончить игру» logs out to the LAN menu; «Новая игра», «Новый герой» and «Выход» end the game first. A lost connection and the hero's death also return to the LAN screens. No single-player menu items are reachable from a LAN game.
* The hero type is the login portrait at «Ok» (`Client.Enter(model)`, as the original's `0x4C` carries the model), not at the server pick: it sets the start village, the team and the look's palette, and the server keeps it (`ModelSetter`).
* World clock (`netplay/clock.go`, `game/lanclock.go`; port rule — the original's clients each ran their own): the server counts game ticks (60 ms, 1 + speed per 60 ms) while anybody is in the world and stops when it is empty; it sends the clock (`MsgClock`: tick, speed, session seconds left) on every entry, when the world empties or fills, at each session start and every 30 s. A client's scene takes its tick from the server's views (time of day, lanview.go); the world speed is the server's (`-speed`, numpad +/− do nothing); the moonlit night is decided from the day number, the same everywhere; the session's time left is shown in the view's top-left corner («До конца сессии»). Verified under Xvfb with the dedicated server, together with the hero type at «Ok» and the LAN menu.
* Items are the server's ([items in the world](#items-in-the-world)): the bag, equipment, jewellery, quiver, the in-hand box, raises, herbs and potions, drops and pick-ups, the pile window, kept between sessions (`SAVITEMS.DAT` → `lanstore`).
* Dialogues and trade are the server's ([dialogues and trade](#dialogues-and-trade)): a right click on a villager with a dialogue opens it, replies run the LAN script rules on the server, the shops sell each player its own stock.
* Not ported: arrows in flight on the clients (the server's arrows are not reported), hirelings (dialogue script 291), the shovel's dig mode and the misc items that need the single-player world (orbs, keys, the whistle, the doll, the lamp, the magnet, the seer's scroll), the LAN HUD (`INTO640R`; the single-player HUD stands in), per-map single-player tables keyed by map number (fixed light, location names) applied to LAN maps, the rating rows on «Рейтинг» (the store has them: `lanstore.Store.Ratings`), «Установки» (state 8), in-game chat, amulets.

## New hero

State 4, drawn by `0x00427D14`, clicks `0x0042E3CA` (jump table `0x0042EB84`, hit test `0x00417934`). It is the single-player creation screen ([new game](konung_new_game.md)): the same 33-hotspot layout and the same class, skill and stat-trade handlers, with the LAN tables below. The hero portraits are replaced by the clan picker, and the preview switches the look. Opening it (`0x0042E0DB`) logs out (`0x44`), clears the server address and resets the template `0xA6E874` (LAN entity layout): the single-player template (Воин; Хар 3, Сил 15, Лов 3, Вын 10; Фехтование, Идентификация; no free points) at **level 13** (single-player 10), gold 1000, no items.

Hotspots `0x0047DE24` (33, 800×600 rects; `LANExe.NewHeroRects`): 0 clan field (31 bytes), 1/2 clan list scroll, 3–6 Купец/Охотник/Вождь/Воин, 7–10 values Хар/Сил/Лов/Вын, 11 «Макс. груз», 12 «Макс. отряд», 13 Кузнечное дело, 14 Плотницкое дело, 15 Фехтование, 16 Меткость, 17–19 Идентификация/Торговля/Знахарство, 20 «Ok» (85,545), 21 «Отмена» (195,545), 22 the hero (610,160; 160×160), 23 clan rows (33,176–361,521; +5, 15 px per row), 24 free points, 25–32 −/+ for Хар, Сил, Лов, Вын. Because free points start at 0, a build is a trade: the cost of each point depends only on its value, so any final stats are reachable when each is within 0 … cap and the points refunded cover the points spent (`LANHeroChoice.Build`). `TestLANHeroTables` checks the hard-coded tables against `LAN_KONG.EXE`.

«Ok» (`0x0042E756`) sets level 1 and the pending flag `[0xA6EAF8]`, backs the hero up (`0xA6E974`), saves `LAN.CFG`, adds a new clan to the list and opens the login; nothing is sent. With the flag set the login answer (`0x00420750`) keeps the built hero, and the login «Ok» shows message 1 «Предупреждение: Старый персонаж будет удален!»: «Ok» (`0x0042DBDB`) connects and sends `0x4C`; «Отмена» (`0x0042D9D8`) clears the flag for the LAN menu. «Отмена» on the screen (`0x0042E826`) returns to the LAN menu. The model is not chosen here: the login portraits (`0x0042ECA2`/`0x0042ECD2`/`0x0042ED02`) set the name index (124/151/10), the model (1/2/0) and the palette of the same look index.

`0x4C` (`0x004179B4`, 0x73 bytes) carries the name, password, clan and the whole hero on every entry. The server's check `0x00447460` accepts a level-1 hero with every stat ≤ 30 and free points ≤ 50 as long as gold and `+0x28` equal the record's; otherwise it needs the record's free points and, above level 1, its stats and class. Skills, model and palette are never checked. A rejected hero (`0x0044B513`) has its record reset (free points 0, gold 100, level 1, every stat 1) and gets message 7.

Port, with a server that decides: the client sends only the choices (`netplay.HeroChoice`: class, combat skill, peaceful skill, the four stats, the look) with the next join after the warning; the server rebuilds them with the screen's rules and refuses anything the screen cannot produce (`ErrHero`, port message «Ошибка: Сервер не принял нового героя»). The rebuild resets level, gold, stats, skills, free points and items, and keeps the rating and counters; the clan changes only with a rebuild (and on the first login). As the original, the preview opens on Михаил and one look index serves every hero type; the type stays a per-session choice at login («Ok»). The preview is drawn like the original: the hero image's top-left at (15, 20) in the 160×160 square at hotspot 22 (`0x004286CA` → `0x0044EE76`, no anchor; the single-player screen uses (60, 20)). Port addition: a right click on the preview shows the look on the next type (Михаил → Волк → Драгомир), a demonstration only that changes neither the build nor the login's type.

## Items between sessions (`SAVITEMS.DAT`)

One `0x200`-byte record per account (handle `[0xF5EC58]`, create `0x00431784` fills `0xFF`), written by `0x00444918` from the hero, read by `0x0044444C` at «Ok» and at a new session. Port: `lanstore` `items` table.

| Off | Size | Content |
|---|---|---|
| `+0x00` | 6 × 7 | equipment: item `+1` (enchantment), `+3` (type), `+0` (category, `0xFF` empty) \| `0x80` (guess: identified by this player), high words of condition `+4` and maximum `+8` |
| `+0x2A`, `+0x2B` | 1, 1 | boxed arrows: type, count |
| `+0x2C` | 5 × 3 | jewellery: `+1`, `+3`, category \| flag |
| `+0x3B` | 32 × 7 | bag, as equipment (arrows keep their count) |

On load, bag items are dropped when category > 12, category ≤ 5 with type ≥ 70, category 9 with type ≥ 14, or category 11 with type ≥ 10 (the amulet parts, types 10–13, but also every other misc item from type 10 on, e.g. the bat wing, type 25). The port applies the filter in `lanstore.LoadItems` and packs the bag from the front again (`lanserver.World.LoadItems`).

## Score and rating

`0x0043B67C(killer, victim, points)` (`gamestate.HeroKillPoints`, `lanstore.Store.Score`): an amulet part delivered on a scoring spot (table `0x004826D0`) = 25 points; a player hero's kill = max(1, 2·victim level − killer level + 1), doubled when the victim carries an amulet part; hireling and monster kills are counted with 0 points. Session end `0x00444150` (`gamestate.SessionRatings`, `lanstore.Store.EndSession`): over the participants (session points ≠ 0), R̄ = mean rating, P = sum of positive points, p̄ = P / n; each rating += (max(points, 0) − p̄) · R̄ / P, clamped to 0 … 10,000,000. Rating table `0x00446FA0` (10000 × `0x7C`, by rating; clan rating = members' mean, a guess): name, clan, amulets, the three kill counters, rating, clan rating, ranks.

## Map window (M)

Draw `0x0041E8EC`, the single-player window's scheme with LAN tables (`gamestate.LANExe.Map`, `MapMarkers`; drawn by `worldMapWindow.drawLAN`): parchment = interface slot 4, picture = `INTO640R.RES` slot 179 (502×361, a 5 × 4 grid of the 20 maps, each framed by its 8 teleports), clipped to row runs. Area per video mode `0x0047EFA4` (16 bytes: int32 x, y, width, height; 800×600: (80, 60), 502 × 361), row offsets `0x00477750`, runs `0x004714D0` — **region = map number** (1–20; 0 = none). Then the number of players per map (the 16 player groups' `+0x1B`) is drawn at `0x0047F004`/`0x0047F058` (int32 x, y per map, from the area's top-left) + 3 (font `0x0078C1A0`). The hit test `0x004176AB` (`0x0044D3D0` on the same runs) only gives a hover id; there is no travel by click. Validation: `gamestate.TestLANMapWindow` (each map's count spot lies in its own region), `game.TestLANWorldMap` (all maps drawn, only the current one tinted); checked under Xvfb (map 1, then map 3 after a teleport).

## Game start

Client «Ok» (`0x004179B4`) sends `0x4C` and waits (state 0, variant 10). Server `0x0044ADB4`: a free slot, the hero from the account, **start map = hero model · 3 + 1** (`0x0044401C`: the model's village), **start cell and facing = the arrival of the first map exit leading to that map** (`gamestate.LANStart`; shipped: model 0 → map 1 (110, 32) facing 2, model 1 → map 4 (66, 57) facing 0, model 2 → map 7 (65, 8) facing 4), placed by `0x00435830` when the cell is free (the fallback search is not traced), items from `SAVITEMS.DAT`, then `0x5A` (the hero's appearance, name, clan) to everyone and `0x8C` to the client: slot, map, entity word (bits 0–11 index, 12–13 weapon mode → entity `+0x0C`: 0 axe, 1 bow, 2 blade; 15 combat stance), (type << 4) | facing, row and col as single bytes. Client handler `0x0042105C`: its hero = entity `slot`, filled from its hero record (HP 1600), the map loaded from `MAPS.RES`, the hero placed; state 10 (`0x0042F620`) loads `INTO`, centres the camera on the hero and enters the game. **Team = hero model**, not the clan. `SERVER` lines 0–2 are the amulet parts' spawn spots (category 11, types 10–12; `0x004349FC`), lines 3–5 the delivery spots of models 0–2 (type 13, 25 points).

Other players reach the client as `0x5A`/`0x1A` (appearance: entity word, HP/16, model and kind, level, palette, equipment, jewellery, bag; players add name and clan, handler `0x00422C9C`) and `0x19` (9 bytes: entity word, (type << 4) | facing, HP/16, row and col bytes; applied on the current map, handler `0x0042294C`); items as `0x00`/`0x40` (`0x0042008C`).

## Fights

The original's server runs the whole world (tick `0x445988` over all 80 groups: groups 0–15 are the players' parties, group = slot; creature and village AI on the server; arrows `0x444CD0`); clients send orders and draw what the server reports. Verified in code:

* A world click sends `0x55` (builder `0x418E90`, server `0x449B24` → `0x446264`, sub-command 0): `+0xC`/`+0xD` row/col, `+0xE` target index + 1, `+0x10` map. A right click on an entity with a dialogue sends `0x43` (the shop request, then the dialogue; [dialogues and trade](#dialogues-and-trade)) only out of the stance, for a group ≥ 16, without Ctrl; otherwise it is an order. With a target in the stance the server shoots (bow `+0x0C` = 1 with arrows) or fights in melee, target in `+0xBB` (index + 1); targets in the own group are ignored.
* Hit `0x43E33C`, damage `0x43E968` on the server; a heavy hit plays the flinch (2 in the stance, 8 out of it), a kill experience `0x43E394` and the death (3/9, `0x4386A0`); the attacker gets xp/4 in `+0x12`. A player attacker scores `0x43B67C(attacker, victim, 0)` (melee `0x445D18`, arrows `0x444FF2`), then `0x5C` to it (`0x448970`, its stats; the account is saved), then loot `0x43BD54` (creatures drop their gold; players keep theirs).
* `0x19` action nibble: 0 idle, 1 walk, 2 flinch, 3 death, 4 shoot, 5 melee in the stance, + 6 out of it; the client starts the action (`0x412450`). `0x1A`/`0x5A` (`0x448524` → `0x422C9C`): entity word, HP/16, (model << 4) | class, level, palette/512, the quiver `+0x38`, equipment 12 bytes, jewellery 10, bag 64, then name 32 and clan 32 for players (`0xA1` bytes, else `0x61`). The draw (`0x4197A2`) reads `+0x0C` as the weapon slot.
* Same team (model) heroes can hurt each other: only the group is compared. No safe areas. A hit on a player marks the attacker in the map record's `+0x4E` when the map's village side (`+0x1E & 3`) is the target's model (orders) or always (arrows) — read as the village's aggressor list (guess).
* Death: at the end of the death action (`0x436A46`) `+4 |= 0x80` and the hero leaves the grid. No respawn: HP 1600 is written on entry (`0x44B263`), at the session's end (`0x448BB8`: every hero back to its village, full HP, out of the stance), and by heals and items.

Messages client → server (type | `0x40`, table `0x482914`): `0x4B`/`0x55` orders (`0x449B24`), `0x4A` item and HUD events (`0x44AC78`), `0x4D` give an item (`0x44BA34`), `0x42`/`0x43` trade (`0x449DB4`/`0x44A3BC`), `0x53` dialogue script function (`0x44BCC4`), `0x57` chat (`0x44C9B0`), `0x5D` stat raise (`0x44CB48`). Server → client: `0x19` (`0x448410`), `0x1A` (`0x448524`), `0x1B` (`0x44875C` → `0x422ED8`, probably a walk path), `0x1C`/`0x5C` (`0x448970` → `0x423180`), `0x12`/`0x52` (`0x448182` → `0x42219C`, probably a shot), `0x00`/`0x40` items (`0x4478B4`), `0x83` the shop of a `0x43` (`0x0042024C`), `0x93` the `0x53` acknowledgement. Not traced: `0x08`/`0x48`, `0x09`/`0x49`, `0x4E`, `0x4F`, `0x50`, `0x51`, `0x16`/`0x56`, `0x5E`, `0x58`.

**Port**: fights run in the server's world ([server world](#server-world)) with the game's own rules (`internal/world`: `Strike`, arrows, `Kill`), as in the original; clients send orders and draw the states. A player's kill is scored by the dedicated server (`lanserver.Host.OnKill` → `HeroKillPoints` for a player victim, a creature or villager counted with 0 points, `lanstore.Score`; the killer's experience `SaveProgress` and `MsgHero` to it, as `0x5C`). Team damage is a server option (`-team-damage`, default true as the original; false: `lanserver.World.TeamSafe`, `Hooks.Protected` — blows between heroes of one type stop, arrows do no harm, right-click orders on a teammate are dropped; `SessionInfo.TeamSafe` tells the clients). The own hero's death (its state `Dead`) does not end the game: the hero lies dead in the world for everyone and its player stays, watching ([life and death](#life-and-death-logout)); it stays dead until a living player reads «Слова Воскрешения» on its map, the session ends, or it leaves and enters again (naked, [items in the world](#items-in-the-world)). Fighters carry the account's class (`lanfight.ApplyHero`).

## Server world

The dedicated server runs the whole LAN world, as the original's server (tick `0x445988` over every group); the game is a viewer of it.

* `internal/lanserver` (engine-free): `Load` builds one `internal/world` World per `MAPS.RES` map (1–20) over one shared `gamestate.Game` from `GAME.RES` (`ParseLANWorld`): each map's walk grid and size, and the map entry (`World.Populate`: creatures placed in their territory and respawned, villagers on their cells; posts stay where `GAME.RES` puts them, inside their buildings' footprints). Frame counts (walk steps, action lengths) come from `GRAPH.RES`/`OBJECTS.RES` decoded once per model, action type and facing (`resfmt.LoadEntityAnimation`), no images.
* Players: slot k (0–15) is group and entity k, as the original. `AddPlayer(slot, model, hero)` builds the hero like the client (`lanfight.Hero`: the type's `GAME.N` hero with the account's values; its gear copied into the world's items) on the type's start (`gamestate.LANStart`, nearest free cell); `RemovePlayer`; `MoveTo` (a jump). On a map the heroes are its World's party members (`World.LAN`): each its own leader (no following, `IdleTick`/`WalkOrder`), groups 0–15 count as party where single-player says group 0 (`World.PlayerGroup`: creatures target them, A does not), a hero ending a walk on an open exit leaves alone (`Hooks.MemberExit`; the runner moves it to the target map after the tick), the settlement pass only for the shops, per player slot ([dialogues and trade](#dialogues-and-trade)).
* Orders: `Walk(slot, row, col)`, `Right(slot, target, row, col)` (world.RightOrder: shoot or melee in the stance, a pick-up walk without a target), `Stance(slot, on)`, `Weapon(slot, mode)`, `Attack(slot)` (A).
* Out: `Step` (one tick of all maps), `Snapshot(map)` (every character: entity, player flag, cell and cell left, walking and walk step, facing, action and step, HP, dead, stance, weapon), `TakeEvents` (sounds, action starts, a hero's map change, a player's kill), `View(slot, viewer)` (the map's states for one player: all after entering or a map change, else only the changed ones and the gone), `PlayerLook`. Hits and deaths show in the states.
* `cmd/konung-server` loads it when the data folder has `GAME.RES`, `MAPS.RES`, `GRAPH.RES`, `OBJECTS.RES`, `konung.exe` and `GAME.0`–`GAME.2` (else it logs why and players cannot enter), runs it on the server clock (the clock runs while anybody is in the world; at most 8 ticks per wake-up, further behind it jumps and counts the skipped ticks), connects it to the session through `lanserver.Host` (`ServerConfig.Start`: the entering player's hero in the first free slot, the account's hero from the store and the type chosen at «Ok»; `OnOrder`; `OnLeave` removes the hero; `Advance` steps to the clock and sends every player its map), and logs a line a minute: tick, ticks per second, time per tick, skipped ticks, characters alive per map (`+Nh` heroes). `scripts/konung-server.sh` copies the files.
* Protocol (`netplay/view.go`; `ProtocolVersion` 8 with the items, the health, the dialogues and trade):

| Message | Direction | Payload |
|---|---|---|
| `MsgEnter` | client → server | the hero type at «Ok» (`0x4C`) |
| `MsgEntered` | server → client | map, cell, facing, slot (`0x8C`) |
| `MsgOrder` | client → server | `walk` (cell), `right` (target entity or −1, cell), `stance` (on), `weapon` (mode), `attack` (`0x55`) |
| `MsgView` | server → client | the own map's characters: entity, player flag, cell, cell left and walk step while walking, facing, action and step, HP, dead, stance, weapon; `Full` after entering or a map change, else the changed ones and `Gone` (`0x19`) |
| `MsgPlayer` | server → client | a player's hero first seen or with a new look: slot, player (name, clan, type), account hero, look (stance, weapon, equipment kinds) (`0x5A`) |
| `MsgEvents` | server → client | sounds at a cell, action sounds by entity |
| `MsgMapChange` | server → client | the own hero took an exit: map, arrival cell, facing |
| `MsgHero` | server → client | the own hero's values after a kill (`0x5C`) |
| `MsgClock` | server → client | tick, speed, session time left |

  Views follow the server tick (sent after every wake-up of the world runner); short JSON keys. Measured on the village map 4 with two heroes and 31 villagers: about 92 KB/s at triple speed (49 views/s), so about 30 KB/s per player at normal speed (`TestHostOverNetwork`).
* The viewer (`game/lanview.go`): `lanView` builds the scene from `GAME.RES` (`ParseLANWorld`) and `MAPS.RES`, with the own hero alone as party member 0 (its slot's entity, group 0 on the client; `lanfight.Hero` with the account, as the server) and runs no `World.Step`: every character the server reports becomes a walker (a `GAME.RES` record, or a player's hero built from `MsgPlayer`, its equipment as item records only drawing reads) whose cell, walk step, facing, action and HP are set from each view; only the idle loops animate locally. The scene's tick is the server's (time of day). Input becomes orders: left click walks, right click on a character with a dialogue out of the stance talks to it ([dialogues and trade](#dialogues-and-trade)), right click on a character attacks it in the stance (the server decides), elsewhere walks with a pick-up, Space, 1/2/3, A; F does nothing (no party). A map change (`MsgMapChange`) rebuilds the scene for the new map and keeps the connection. Items: [items in the world](#items-in-the-world). The map window counts only the heroes on the own map (the server reports only that map).
* Cost: 269 characters on 20 maps; one tick of all maps ≈ 0.26–0.45 ms (`BenchmarkTick`, `TestWorldRuns`), the budget is 60 ms.
* Verified under Xvfb with the dedicated server and two game windows: both show Драгомир's village with `GAME.RES`'s villagers at the same places, a walk on one shows on the other, a PvP fight by orders ends in «Ivar killed Olaf: 2 points» and (before the [life and death](#life-and-death-logout) rules) the victim's game over, and a hero walking onto the disc by the start pad goes to map 5 and fights its creatures (the pack joins in). Verified by tests on the real files (`internal/lanserver`): all maps load and run (creatures alive and moving after 600 ticks), a hero walks by an order onto an exit and arrives on the target map (event and snapshot), a hero ordered at a creature fights it to the end, two heroes fight (the snapshot agrees with the records); and the real server binary with a scripted client: the hero on map 7 at Михаил's start, the clock advancing while it is in, stopping when it leaves.
* Not yet: building hits (incendiary arrows fly through buildings: `Hooks.BuildingHit` is nil), the settlement pass beyond the shops (tribute, buildings, training), hirelings in player parties, respawn of the world at a session's end (`0x00446900` re-reads `GAME.RES`).

## Items in the world

The server keeps every item (the original's server: items `0xC4E1B8`, `0x00`/`0x40` item records to clients); the client sends its item clicks as orders and mirrors what comes back (`netplay/items.go`, `lanserver/items.go`, `game/lanitems.go`; `ProtocolVersion` 6).

| Message | Direction | Payload |
|---|---|---|
| `MsgOrder` `item` | client → server | the click: `bag` (cell; right click = use), `equip` (window hotspot 8–13), `jewel` (box 0–4), `box` (the in-hand box), `self` (the held item on the own portrait: use or drink), `drop` (the held item to the ground under the hero), `return`, `boxclear` (the window or strip opened, `0x004246D1`), `raise` (row), `auto` («АВТО»), `pile` (the pile window's «Ok»/«Закрыть» with its four lists) |
| `MsgInventory` | server → client | the own hero's record (bag, equipment, jewellery, quiver, gold, level, stats, skills; the client keeps its cell, facing, action, HP and the stance and death bits from `MsgView`), the 16-byte record of every item it holds, the hand (held item, cursor, box) |
| `MsgPiles` | server → client | every active pile on the own map (index, cell, gold, items) and their items' records |
| `MsgPileWindow` | server → client | the pile window open (pile, map, its four lists) or closed |
| `MsgEvents` `msg` | server → client | a status-line text for the own hero (a pick-up's or an item click's message) |

* Rules: the server applies each click with the single-player functions on the hero's world record and a hand of its own per player (`gamestate.Game.ClickBag`, `UseBagItem`, `ClickEquipment` with `HandSlot`, `ClickJewellery`, `ClickBox`, `ClickPortrait`, `Raise`, `ToggleAutoLevel`; a drop as `game.dropHeld`). Herbs and potions are drunk on the server, so healing by potions is the server's. Misc items run with `gamestate.Game.World` nil: the ones that need the single-player world do nothing (orbs, keys, whistle and pipe, doll, lamp, magnet, the seer's scroll); the shovel's dig mode is not offered. Others (books, the lost map's reveal, skills) apply.
* Pick-ups: a right click on a pile walks there with the pick-up (`world.Arrive`); over the weight or bag limit the pile window opens for the hero picking up (`world.World.Arriving`, `Hooks.OpenPileWindow`); its «Ok» comes with the client's lists, which must move only the window's own items (the bag's between bag and offer, the pile's between pile and take), and `gamestate.Game.Apply` checks the limits; after «Ok» the window shows the pile again unless it is gone. «Закрыть» always closes it (single-player's «Закрыть» keeps it open over a limit; Escape closes it — the port closes either way). Loot from kills is a pile like any other, seen by everyone on the map.
* Looks: a player's equipment change (equip, unequip, wear-out) changes its `MsgPlayer` look for the others on the map, also while it stands still.
* Kept between sessions: `Host.Load` at entering, `Host.Save` at leaving and at the session's end and server stop (`SaveAll`): the hero's values (`lanstore.SaveProgress`: level, gold, free points, stats, skills) and its items (`lanstore.SaveItems`: equipment, jewellery, bag, arrows with their count; the held item goes back first). Condition and maximum keep their float; herbs' and misc items' other data there is stored as 0 when it is not a number.
* Starting gear and death, the original server's rules (the server's memoir, gospitaliers.narod.ru/knyaz_server.htm, and the user: a new hero is given a knife):
  * A new account and a hero rebuilt with «Новый герой» start with only the knife: the item every `GAME.N` hero carries in the blade slot (category 2, type 18; `lanserver.World.AddPlayer`). The store's `starter` flag (schema 4: set at creation and rebuild, taken once by `TakeStarter`; the migration gives it to accounts that never saved items) decides; an account whose items are gone otherwise enters with nothing.
  * Death, whatever killed the hero (a player, a creature, villagers, poison; `Host.deaths`: HP 0): «персонаж падал на землю, его мешок становился общедоступным» — the bag goes into the pile on its cell for anyone, the owner too (`DropLoot`); the worn items (equipment, jewellery, arrows) are kept with the `dead` flag (`Host.Died` → `lanstore.Died`); the gold stays with the hero (the source says nothing; the original's loot drops only creatures' gold).
  * Entering again while dead: «входил он в игру уже голый, а его одетые вещи отправлялись в страну поющих вещей» — naked: `lanstore.Revive` deletes the worn items and clears the flag.
  * A session's end while dead: «мертвые персонажи оживали с надетыми доспехами, но … с пустым мешком» — online, the hero is revived at its start with the worn items and an empty bag (`Host.EndSession`, [life and death](#life-and-death-logout)); offline, `lanstore.EndSession` clears the flag, so the next entry has the worn items and an empty bag.
* Size: an inventory message is about 2.8 KB and goes only when something changed (`TestItemsOverNetwork`).

## Dialogues and trade

### The original (`LAN_KONG.EXE`, traced)

* **Right click** on a character with a dialogue (`+0x3A` ≠ `0xFF`), of a group ≥ 16 (not a player's hero), out of the stance (`+3` bit 4), Ctrl up (`0x9EB9FC`) (`0x00416536`, `0x00416689`, `0x00416770`): the client sends **`0x43`** (`0x004194C0`: the entity index) and waits (`0x9EBA3C` counts open requests).
* **Server `0x43`** (`0x0044A3BC`): no dialogue → nothing. Else the post (`0x004384B4`: the index + 1 of the 5 posts `+0x40C` of the settlement whose village group is the entity's, 0 none) gives t = post − 1. t = 1 healer, 2 merchant, 3 smith: the hero's `+3 |= 8`, and **`0x83`** carries settlement·64 | t·16 | slot and the shop **of this player's slot**: healer 3 empty entries then 25 from `+0x448 + 0x38·slot + 6`, merchant 32 from `+0x7C8 + 0x40·slot`, smith 23 from `+0xBC8 + 0x2E·slot`, each entry the item's category, index, type and condition or count (8 bytes). Anyone else: `0x83` with 0.
* **Client `0x83`** (`0x0042024C`): writes the stock into its copy of the settlement (`+0x448…`, slot `0x9EBA50`), copies the party's bags, and **opens the dialogue itself** (`0x0042CA18`, the single-player `0x004364F0`; `QUESTR.RES`). The dialogue runs on the client: conditions, flags and lines with the single-player engine; the **quest flags live in the client's memory** (nothing sends or saves them).
* **Script functions** (client dispatcher `0x0042AF60`): ids 0–111 (a group hurt, a map cleared) → 0; 112–165 take a quest item → sends `0x53` (id − 11) and returns 0 (`0x0042BCEC`); 166–219 give one → sends `0x53` (id + 0x23) and returns 1 (`0x0042B074`); 220–273 has one → the bag check (`0x0042BD0C`); from 274 the table `0x0047F418` (8 bytes per id: flag at +4 = also send `0x53` with id − 274, function at +8). Stubs returning 0 (`0x0042B054`): 274, 278–281, 283, 292, 304, 311, 314–317, 319–323, 326–328, 336–343, 345–348, 353–361, 365. Sent: 276, 282, 284–291, 293–301, 331, 332, 334, 335, 344, 362–364. The rest run on the client as single player's.
* **Server `0x53`** (`0x0044BCC4`, switch on id − 274): 276 blessing (`+0x3C` = 70); 282 repay a loan (the slot's bit in the settlement's `+0x4C` and gold ≥ 120: bit cleared, gold −120); 284 a loan (bit not set: set, gold +100); 285–290 / 293–298 gold −/+; 291 **hire** (`0x0044BED7`, into the player's group); 299–301 experience (and `0x5C`); 331 identify (`0x0043F288`); 332 dismiss (the NPC must be in the player's group); 334 **HP = 1600** (`0x0044C374`; the healer's skill does not grow); 335 the same for the party (`0x0044C38D`); 344 curse (`0x004379D4`); 362 repair (the smith is post 3, `+0x426`); 363 nothing (the case is empty); 364 lift the curse (`+0x3B` = −1). Ids from 0x64 (the quest items) fall to the empty default: **no quest item is ever taken or given on the server**.
* **Trade** (script 275 on the client, `0x0042B350`): the single-player window with the slot's stock: posts 2–4 (1-based) sell with 99999 coins (healer 24 entries from `+0x448 + 0x38·slot + 6`, merchant 32, smith 23; mode ± p by `0x0042C0A0`, the settlement's `+0xEA8` bit `0x10`), no weapon filter; anyone else barters with its bag and gold. «Ok» sends **`0x42`** (`0x004190D0`): the hero's gold and trade skill **as the client computed them** and the list of item moves (bit 15 sold, bits 13–14 the party member). **Server `0x42`** (`0x00449DB4`) takes them as sent (the hero's gold `+0xE` = the client's; no price check), moves the items, destroys what a shop bought, and after a deal with the healer or the merchant restocks the slot (`0x0044A255` → `0x0043C764`).
* **Shops per slot**: the LAN settlement pass (`0x00440C70`) runs the healer (`0x0043ABCC`) and the smith (`0x0043AF9C`) for **all 16 slots** of each settlement, the healer's cycle timer `+4` shared; the merchant restock `0x0043C764(slot, settlement)` (the single-player `0x00418F0C`, the same item rules incl. misc items `rand() % 10`) runs after a deal, for each slot in the world at the session reset (`0x00446AD1` clears every stock, `0x00446B45`), and at `0x0044B971` for all three villages of a slot after freeing its merchant stock (the enclosing message not identified; probably the hero's entry).

### The port (`gamestate/lanscript.go`, `lanserver/talk.go`, `netplay/talk.go`, `game/lanitems.go`)

* **Server-authoritative** (a port rule): the server runs the dialogue (`gamestate.Talk` with `LAN`: the LAN script rules above; `Party` = the hero's group, `Loans` = the settlement's per-slot bits, `Slot`) and the trade (`gamestate.Trade`, `Balance`, `Apply`); the client shows what it is sent and sends choices.
* Orders: `talk` (`Target`, the original's `0x43`): the server opens the dialogue when the character is on the hero's map, of the world (entity ≥ 16), alive, with a dialogue the LAN world opens (`gamestate.LANTalks`, below; `QUESTR.RES` loaded), the hero alive and out of the stance, no window open, and within **`TalkRange`** = 800 world pixels in x and y (one screen; the original's server checks nothing). `reply` (`Index`): a reply not offered is ignored. Item actions `trade` (window 7's «Ok»/«Закрыть» with the four lists) and `close` (Escape: no deal, also for the pile window).
* Server → client: `MsgDialogue` (open, the NPC, the lines' and replies' `QUESTR.RES` text ids, the greeting sound) and `MsgPileWindow` with `Trader` (the NPC, mode, both sides' money, the trader's trade skill) and the goods' item records; both only when they change.
* A deal is checked against the window as it is now (`openTrade`: the hero's bag and the goods): the lists must hold exactly those items, else nothing happens and the current window is sent; then the coins are balanced and `Apply` runs (limits, «Слишком мало даешь!»). After an accepted deal with the healer or the merchant the slot restocks (`0x0044A255`); the window reopens with the new state; «Закрыть» closes.
* **Shops** (`gamestate.LANShop`, `Game.WithShop`, `LANShopPass`, `ClearShop`, `FreeMerchant`): each settlement keeps 16 per-slot shops (from `GAME.RES`, empty there), laid over the single-player shop offsets for the single-player code. Every 16 ticks (`SettlementTickOffset`) the healer and smith run for all 16 slots; entering the world frees and restocks the slot's merchant in all three villages (`0x0044B971`); a session's end clears every stock (the port also frees the items) and restocks the slots in the world. The smith's job timer is kept per slot (where the original keeps it was not traced). The trade does not freeze production (the server has no window 7).
* **Not sold** (the original server's rules, a port filter on the goods list: `LANNotSold`): Яблоко познания, Дупликатор, Лопата, Медное зеркало колдуна, Соколиная лапка, and the herbs Яд and Масло (no poisoned weapons or incendiary arrows in the network game). They stay in the stock unsold (the original code still makes the duplicator and the falcon foot: misc `rand() % 10`).
* **Quest flags**: per player, from `QUESTR.RES`'s initial flags at every entry (the original keeps them in the client's memory; a guess that they start fresh with each game).
* **Deferred**: 291 hire returns 0 and the hero sees «Наёмники в сетевой игре пока не перенесены.» (no hirelings in LAN parties yet); 332 dismiss returns 0.
* **Which characters talk** (a port rule, `gamestate.LANTalks`): `GAME.RES` gives its characters single-player dialogue numbers and the original opens the number as it is (`0x0042CA18`: starts table `0x802190`). Only the post roles' shared dialogues fit the network game: 100 the voevoda, 101 the healer, 102 the smith, 103 the merchant. The others open single-player quest dialogues: the elders 105 (map 7: Глеб, the elder of Бережки), 106 (map 1: the stranger's greeting «Приветствую тебя, друг!»), 107 (map 4, two characters: the lady with the horse Эпофодит), the six guards 104 (the old man and the spiders), the villagers 109/110/111 (18/17/18: the horse lady's companion, the wise man's cure quest, «Ярл»), the animals 108/112 and the three objects 6. Both installed files (`questr.RES`, `Quest_r.res`) give the same lines for them (`Quest_r.res` is the single-player file with typo fixes: 41 013 text ids and 116 starts differ). And the village flag that 302 tests (settlement `+0xEA8` bit `0x10`, LAN `0x0042C0A0`) is set on every village at load and session reset (`0x004106EA`, `0x00446ACA`), so no elder treats any player as its own. So the port opens only 100–103; the rest are silent (the user's choice, 2026-11-19). Plain villagers are meant to be hired in a later piece (the original server's hirelings, ~150 coins), with a dialogue of their own then.
* Verified: tests on the real files (`TestTalkAndTrade`: range, stance, entity and reply checks, the per-slot merchant stock, the duplicator not offered, a purchase and a sale with the gold and bag, a list with a foreign item refused, «Закрыть»; `TestHealerHeals`: the healer's reply heals for money; `TestShopsPerSlot`: healer potions in slot 0's and slot 5's stock; `TestTalkOverNetwork`: the dialogue, the replies to the trade, a purchase and Escape over the network; `TestOnlyRolesTalk`: village 7's elder and a guard stay silent, the merchant talks). ## Life and death, logout

Rules of the original server (gospitaliers.narod.ru/knyaz_server.htm) and port rules, in `lanserver.Host`, `lanserver.World` and `lanstore`:

* Death keeps the player in the game: the hero lies dead in the world (its last death step, visible to everyone); its player stays connected and watches (orders are ignored by the client and the server; Esc gives the in-game LAN menu, «Закончить игру» leaves). The client plays no `GAMEOVER.FLM` in a LAN world (`Menu.Update`: `GameOver` only off LAN).
* Revival: «Помочь в этом случае могло либо окончание сессии либо если кто-то из (живых) игроков прочтет на той же локации слова воскрешения». A living player using «Слова Воскрешения» (misc type 6, `gamestate.UseMisc` sets `Game.ReviveAll`) on a map revives every dead player's hero there (`World.reviveHeroes` → `world.World.Revive`, the single-player `0x00414B3C`: its cell or a free one next to it, its HP rule), wearing what it wore (its bag lies where it fell). Dead creatures and villagers stay dead (single player's `0x00414FFB` revives them too; the source names only players). `Host.deaths` sees the revival and saves the hero alive (`Save`; the dedicated server's `saveHero` clears the dead flag, `lanstore.Alive`).
* The session's end (`Host.EndSession`, as `0x00448BB8`): every hero in the world goes back to its type's start (`World.ToStart`: a map change when elsewhere), alive (a dead one revived wearing what it wore; its bag lay where it fell), full HP, no poison, out of the stance, and is saved; `lanstore.EndSession` clears every dead flag and heals every account.
* Health kept (a port rule against leaving to heal: the original enters with HP 1600, `0x0042105C`): the hero's HP and poison are saved with its values (`lanstore` schema version 5: `hp`, `poison`; `World.Progress`, `SaveProgress`) and restored on entering (`lanfight.ApplyHero`). Full HP: a new or rebuilt hero, entering again after death (`lanstore.Revive`), the session's end.
* Logout (the source: leaving from the home village removed the hero at once; from anywhere else it «оставался там неконтролируем 3 минуты»). Leaving in the home village (map model·3 + 1), or dead, takes the hero out at once (saved unless dead). Elsewhere it stays in the world uncontrolled for 3 minutes (`LingerTime`; it can be attacked and killed, and its death is kept as any death), then goes and is saved. Meanwhile its player cannot enter: `Host.Start` returns `netplay.ErrHeroLeaving`, the server answers `ErrLeaving`, and the client shows message 8 «На сервере идет выход персонажа из игры / Повторите вход в игру через некоторое время» (the original's).
* Villages: the LAN server's village AI is single player's (`0x0043A327` → `0x00437E28`, the random step of `0x00413A84` with fixed ranges 40 rows / 20 columns, i.e. R = 20, C = 10) and keeps villagers inside their group's rectangle (+0x08/+0x0C/+0x10/+0x14), which the server never rewrites. But `GAME.RES` gives all three village groups (16–18) the rectangle rows 0–128 × columns 0–64: a `MAPS.RES` map's whole fine grid (64 × 32 tiles), so in the original data the villagers may roam the map. Port rule (`lanserver.villageBounds`): a village's area is the box around its villagers' and posts' cells as `GAME.RES` places them, widened by 4 rows and 2 columns; the step ranges are the LAN server's (`world.NPC.StepRows`/`StepCols`; single player keeps its view-size ranges).
* Tests: `lanserver` `TestDeadStaysAndRevives` (over the network: the dead stay connected and see their corpse, orders from the dead do nothing, a living player's «Слова Воскрешения» revives with the knife kept, saved alive, walking again), `TestLingerOnLeave` (home: gone at once; away: lingers, entering again refused with `ErrLeaving`, gone and saved after the time, entering works again), `TestHealthAndSessionEnd` (the saved HP and poison on entering, saved on leaving, the session's end: back at the start alive with full HP, saved), `TestVillagersStayHome` (6000 ticks on maps 1, 4, 7: no villager leaves its village area; 81 moved); `lanstore` `TestHealthKept`, `TestMigrateV4`.
* Verified under Xvfb with the dedicated server and two windows: Ivar kills Olaf («Ivar killed Olaf: 2 points», «Olaf died», no «left»); Olaf's window stays in the world showing his corpse in blood with Ivar standing over it and the dead portrait; Esc gives «Вернуться в игру» / «Закончить игру»; Ivar's window shows Olaf's corpse after walking off. The revival and the 3-minute linger were checked by the tests only.
